# Task Design

## 适用与边界

- 适用：完整业务功能、跨模块改造、外部集成、数据迁移，或变更业务流程/状态、DB Schema、公共 API、权限、消息、兼容性、并发/幂等/事务等高成本契约。
- 用户明确要求方案或设计文档时也使用。小修复、单纯调查、低风险局部调整和模糊探索目标不强制设计。
- 本 Skill 只维护稳定设计基线 `design.md`；执行进度与返工状态由 `task-execution` 的 `tasks.md` 维护。
- 读取项目规则、现有代码/调用方、已有设计及约定，避免脱离现状重新设计。
- 文档位置优先遵循项目约定，其次 `work-convention`，否则 `work/任务/<任务名>/design.md`；同一任务仅一个主设计。
- 编写时读取 `references/任务设计规范.md` 和 `templates/design-template.md`，只采用任务需要的章节。

## 建立设计基线

1. 明确背景、目标、非目标、范围、现有能力与关键取舍。
2. 按需设计 Flow/状态、Data/DB、API、集成、迁移和技术结构；普通业务功能优先覆盖 Flow + Data/DB + API。
3. 明确权限、失败路径、幂等、并发、事务、兼容与回滚等实际风险；不要虚构业务规则或过度设计。
4. 为可验收结果定义 `AC01` 等稳定 ID，逐项写明验收对象、验证方式和通过条件；不要按 Controller/Service 等代码层定义 AC。
5. 将未知事项分为阻塞确认项（影响核心行为/高成本契约）和非阻塞待确认项；阻塞项未解决不得实施。

## 对抗式设计审查

- 设计完成后必须 Review，优先独立只读 Reviewer；不可用则同上下文对抗审查，并如实记录 `审查模式：independent | same-context`。不要求固定 Agent 数量或额外编排工具。
- 重点检查需求遗漏、状态/异常、数据与历史兼容、API/集成、权限、并发/事务、验收可测性及过度设计。
- Finding 按 Critical / High / Medium / Low 分级，附可核查证据和建议；Critical 或 High 阻塞 PASS，Medium/Low 记录但默认不阻塞。
- Review FAIL 时修订并复审，最多自动修订 3 轮；仍有 Critical/High 则停止，向用户交付未解决的问题，不伪称 PASS。
- PASS 要求 Critical = 0、High = 0、高成本契约闭合、关键 AC 可验证，未知事项已正确分类。

## 人工确认闸门

1. `design.md` 记录 `设计审查`、`审查模式`、`设计确认` 状态。
2. Review PASS 后，先解决阻塞确认项；涉及设计修改则重新 Review。
3. 阻塞项清零后请用户明确确认设计；确认前停止，不生成执行任务、不修改业务代码。
4. 用户附条件改变高成本契约的“确认”不算最终确认；先更新设计、重新 Review、再请求确认。
5. 只有 `设计审查 = PASS`、`阻塞确认项 = 0`、`设计确认 = 已确认`，才可进入 `task-execution`。
6. 实施中若高成本契约变化，更新设计并重置审查/确认状态；受影响实施暂停，重新走审查和人工确认。低成本实现细节不必重走。

## 完成与权限

- 交付唯一 `design.md`、关键方案与取舍、AC、风险、待确认项及审查/确认状态；只要求设计时到此停止。
- 设计审查不能代替用户确认；不得凭自报 PASS 跳过证据或阻塞项。
- 不擅自 commit、push、deploy、写入生产/共享数据、使用凭据或执行不可逆操作；遵守项目既有授权及用户明确许可。
