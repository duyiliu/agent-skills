# Task Design

## 目标

建立一个**足够、清晰、可验证的 `design.md` 设计基线**，只负责“做什么、哪些高成本契约不能随便变”。

不在 `design.md` 维护执行进度、完成勾选或返工队列；这些属于 `tasks.md`，由 `task-execution` 维护。

## 何时触发

满足任一条件时使用：

- 用户明确要求正式设计、可实施方案或 `design.md`；
- 新增完整业务功能 / 模块、外部系统接入、跨系统流程；
- 核心数据结构、迁移、架构或跨模块改造；
- 会形成或改变高成本契约：
  - 核心流程 / 状态机
  - DB Schema / 核心数据模型
  - 公共 / 外部 API
  - 权限
  - 消息 / 事件
  - 数据迁移 / 兼容
  - 并发 / 幂等 / 事务
  - 多系统协作边界

同一既有架构下，仅加字段、参数、守卫、开关或既有 AC 分支，默认直接做；只有真正改变上述边界才进入本 Skill。

### 不触发

- 仅讨论方案、比较实现方式、回答架构问题；
- 小 Bug、单纯排错、单条 SQL、单字段 / 单接口小改；
- 纯 UI / CSS、低风险可逆重构；
- 仅内部实现变化且业务契约不变；
- 需要反复试出来的模糊探索目标。

讨论阶段先在对话里收敛。用户随后要求“按这个方案实现”时，再按是否涉及高成本契约决定是否进入正式设计。

判断核心：

> 这个任务是否值得在编码前建立一个稳定的设计基线。

## 工作流

### 1. 读取现状

先读项目规则、相关实现、调用方和已有设计资料。沿用现有约定，不脱离项目重新造一套。

### 2. 确定文档位置

优先级：

1. 项目已有约定；
2. `work-convention`；
3. 默认 `work/任务/<任务名>/design.md`。

同一任务只保留一个主 `design.md`。

创建或大改设计时读取：

- `references/任务设计规范.md`
- `templates/design-template.md`

### 3. 建立设计基线

至少明确：

- 背景、目标、非目标；
- 范围与影响范围；
- 可复用现有能力；
- 高成本契约；
- 必要边界、风险和待确认项。

按实际需要覆盖 Flow、Data/DB、API、集成、迁移等维度，不为“文档完整”填无关章节。普通业务功能通常优先覆盖 **Flow + Data/DB + API**。

### 4. 定义验收

使用 `AC01`、`AC02` 等稳定 ID。每个 AC 说明：

- 验收什么；
- 如何验证；
- 什么结果算通过。

AC 描述结果，不写 Controller / Service / Mapper 等代码任务。

### 5. 自查

至少检查：

- 目标、范围、方案是否一致；
- 流程、状态、数据、接口是否闭合；
- 权限、异常、幂等、并发、兼容是否遗漏；
- 是否复用已有能力；
- 是否出现不必要的新表、新接口、新抽象；
- 是否把未知业务规则当成事实。

未知信息分为：

- **阻塞确认项**：会改变核心行为或高成本契约；
- **非阻塞待确认项**：不影响当前高成本契约。

## Design Review 与人工确认

默认一个 Builder 维护 `design.md`，自查后交给一个**只读 Reviewer**。优先独立上下文；不可用时使用 same-context，并记录实际模式。Reviewer 只找问题，不直接改设计。

主流程：

```text
起草 design.md
→ Design Review
→ 修复 Critical / High
→ 增量复审
→ PASS
→ 阻塞确认项清零
→ 用户确认当前设计版本
→ 停止设计阶段
```

规则：

- `Critical / High` 阻塞确认；`Medium / Low` 记录但不默认返工。
- 首审覆盖当前设计和必要现状；复审只看未闭合 finding 与受影响范围。
- 每个设计审查阶段默认最多 **3 轮**。第 3 轮仍 FAIL 时停止自动循环并报告剩余阻塞项。
- PASS 后停止主动“继续优化设计”，不要为了清空 Medium / Low 再开一轮。
- 有阻塞确认项时先让用户决策，不请求总体确认。
- 只有用户对**当前已审阅版本**明确、无条件确认后，才进入实施。
- 用户确认时若同时改变高成本契约，不算确认：更新设计、重新审查受影响范围，再确认。
- 普通实现细节不要求用户确认。

仅在以下情况需要读取 `references/design-review-lifecycle.md`：

- Review FAIL，需要进入复审 / 返工；
- 恢复旧任务，需要继承轮次、范围或 Reviewer；
- 已确认设计发生高成本契约变化；
- 需要处理审查范围继承、版本失效等状态细节。

## 实现中发现设计变化

先区分：

- **实现没做到已确认契约** → 修实现，不重开设计；
- **已确认高成本契约本身要改** → 更新 `design.md`、使受影响确认失效、回到本 Skill 审查并重新确认。

低成本实现细节变化不回填设计，也不重新找用户。

除设计确认外，只有缺失核心业务规则、不可兼容方案无法判断、需要凭据 / 授权、不可逆外部动作或明显数据安全风险时才中断找用户。

## 完成条件

设计阶段完成时应满足：

- 唯一 `design.md` 已建立；
- 高成本契约、关键边界、风险和 AC 清楚；
- 阻塞确认项 = 0；
- Design Review = PASS；
- 审查模式与有效范围有记录；
- 用户已确认当前设计版本，或当前请求仅要求设计且正等待确认；
- 没有混入动态执行状态。

## 与其他 Skill 的关系

- `task-design`：定义稳定设计基线。
- `work-convention`：定义文档位置和生命周期。
- `task-execution`：把已确认设计转成任务并实施。
- Bug / 调查 / 重构 / 性能专项优先走对应 `goal-*`，不能因为步骤多就切成本 Skill。

## 回复约定

Review PASS、阻塞确认项清零后：

```text
已创建/更新：<design.md>
设计审查：PASS（independent | same-context）
设计基线：<核心摘要>
关键取舍：<重点>
阻塞确认项：无
非阻塞待确认项：<有则列出>
下一步：请确认当前设计版本；确认后进入 task-execution
```

收到明确确认后记录确认依据和设计版本；若用户原始目标包含实现，则继续进入 `task-execution`。
