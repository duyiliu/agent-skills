# Task Design

## 入口与产物

- 适用：完整业务功能、跨模块改造、外部集成、数据迁移，或变更业务流程/状态、DB Schema、公共 API、权限、消息、兼容性、并发/幂等/事务等高成本契约；用户明确要求设计时也适用。
- 不因任务步骤多就接管专项修复、调查、行为不变重构、性能优化或模糊探索任务。
- 只维护稳定设计基线 `design.md`；动态执行状态属于 `task-execution` 的 `tasks.md`。
- 先读取项目规则、相关实现/调用方和已有设计。文档位置优先项目约定，其次 `work-convention`，否则 `work/任务/<任务名>/design.md`；同一任务只保留一个主设计。
- 创建或修改时读取 `references/任务设计规范.md`、`templates/design-template.md`；按实际风险选择章节，不填无关内容。

## 设计基线

1. 明确背景、目标、非目标、范围、已有能力与关键取舍，不臆造未知业务规则。
2. 按需设计 Flow/状态、Data/DB、API、集成、迁移、技术结构；普通业务功能优先覆盖 Flow + Data/DB + API。
3. 明确失败路径、权限、幂等、并发、事务、兼容、历史数据及必要回滚策略；优先复用已有实现，避免无根据的新表、新接口和抽象。
4. 为稳定的可验收结果定义 `AC01` 等 ID：验收对象、验证方式、通过条件。AC 不写成 Controller/Service/Mapper 等实现步骤。
5. 将未知分为 **阻塞确认项**（影响核心行为或高成本契约）和 **非阻塞待确认项**；前者解决前不能实施，后者不应阻塞合理推进。
6. 在设计文档记录 `设计审查：待审查 | PASS`、`审查模式：independent | same-context`、`设计确认：待确认 | 已确认`。

## 设计审查

- 人工确认前必须做对抗式 Design Review：优先独立、只读 Reviewer；不可用时允许 same-context 自审，但必须如实记录模式，不能声称独立审查。无需固定 Agent 数量。
- Reviewer 试图推翻设计可实施性，重点检查：目标/范围遗漏、非法状态与恢复路径、DB 唯一性/历史兼容、API 超时重试幂等、权限/并发/事务、迁移风险、AC 可测性及过度设计。
- Finding 分 `Critical / High / Medium / Low`；附证据、影响和建议验证方式。Critical/High 阻塞 PASS；Medium/Low 记录但默认不阻塞。
- FAIL 后由 Builder 修订、再 Review，**最多自动修订 3 轮**。三轮仍 FAIL 时停止并报告剩余阻塞问题，不能包装为已通过设计。
- PASS 必须同时满足：Critical = 0、High = 0、关键高成本契约闭合、关键 AC 有可执行验证方式、未知事项已正确分类。
- Review PASS 不等于用户确认；审查与确认是两道独立闸门。

## 人工确认状态机

1. 设计审查未 PASS：不得请求总体设计确认，更不得生成执行任务或修改业务代码。
2. Review PASS 但存在阻塞确认项：先向用户询问具体决策；得到答案后更新设计，重置审查为待审查，再 Review。
3. Review PASS 且阻塞项清零：向用户展示关键设计与取舍，等待**无条件的明确确认**；沉默、模糊认可不算确认。
4. 用户说“可以，但把 X 改成 Y”等附条件回复，若改变高成本契约：不算已确认；先更新设计、重新 Review、再次请求确认。
5. 只有 `设计审查 = PASS`、`阻塞确认项 = 0`、`设计确认 = 已确认`，才可进入 `task-execution`；用户仅要求设计时到此停止。
6. 实施中发现高成本契约必须改变：更新 `design.md`，重置审查与确认状态，暂停受影响实施，复审并重新取得用户确认；低成本实现细节不需重新确认。

## 交付与安全

- 输出唯一 `design.md` 路径、设计摘要、关键取舍、AC、审查模式与状态、阻塞/非阻塞确认项和下一步。
- 独立 Reviewer 只找问题，不直接修改设计；Builder 负责修订与复审。
- 只有缺失关键业务决策、必要授权/凭据、不可逆或生产风险时才额外中断；普通低成本实现选择无需逐项请示。
- 不擅自 commit、push、deploy、写生产/共享数据、使用凭据或执行不可逆操作；遵守项目授权与用户明确许可。
