# Task Design

## 职责

为值得先设计的研发任务建立一个**足够、清晰、可验证的 `design.md` 设计基线**。

本 Skill 只负责“要做成什么、哪些契约不能随便变”，不承担执行进度管理。

1. 判断任务是否值得先设计。
2. 读取项目规则、现有实现和已有资料。
3. 确定设计文档位置。
4. 明确目标、范围和高成本契约。
5. 创建或更新唯一主设计文档 `design.md`。
6. 检查关键设计是否闭合、可验证。
7. 在人工确认前执行内置的**对抗式设计审查**：优先使用独立 Reviewer；不可用时降级为 same-context review，并明确记录模式。

**不在 `design.md` 中维护当前阶段、最近进展、下一步、完成勾选或返工队列。**
这些动态执行状态属于 `tasks.md`，由 `task-execution` 维护。

完整设计原则见 `references/任务设计规范.md`；创建设计文档时读取 `templates/design-template.md`。

## 何时触发

满足任一条件即可：

- 用户明确要求先设计、出方案、写 design / 设计文档。
- 新增完整业务功能或模块。
- 接入新的外部系统、第三方服务、消息链路或跨系统流程。
- 新增或调整数据库核心结构、数据迁移、历史数据改造。
- 跨模块技术改造、架构调整或需要明确迁移路径的重构。
- 改动会形成或改变高成本契约，例如：
  - 核心业务流程 / 状态机
  - 数据库结构 / 核心数据模型
  - 公共 / 外部 API
  - 权限边界
  - 消息 / 事件契约
  - 数据迁移 / 兼容策略
  - 并发、幂等、事务边界
  - 多系统协作关系

默认不触发：

- 小 Bug、单纯排错
- 单条 SQL / SQL 调优
- 单字段调整
- 单接口小改且不改变公共契约
- UI / CSS 小调整
- 局部、可逆、风险低的重构
- 仅修改内部实现且业务契约不变
- 需要通过反复尝试判断结果的探索型模糊目标

判断核心：

> **这个任务是否值得在编码前建立一个稳定的设计基线。**

## 执行流程

### 1. 读取项目上下文

优先读取：

- `AGENTS.md`、`CLAUDE.md`、rules、README 等项目规则
- 与当前任务相关的现有实现和调用方
- 数据库、API、权限、错误码、消息、配置等既有约定
- 已存在的 `work/`、`dev/`、`docs/` 和设计文档

先理解现状，再设计；不要脱离已有项目重新造一套风格。

### 2. 确定文档位置

按以下顺序：

1. 当前项目已有明确设计文档约定 → 沿用。
2. 可用 `work-convention` → 按其存放规则执行。
3. 两者都没有 → 默认：
   ```text
   work/任务/<任务名>/design.md
   ```

如果项目已经使用历史 `dev/` 或英文目录，继续沿用现有风格，不创建第二套体系。

同一任务只保留一个主 `design.md`。

### 3. 读取规范和模板

必须读取：

- `references/任务设计规范.md`
- `templates/design-template.md`

根据当前任务只保留必要设计内容，不为了“文档完整”填充无关章节。

### 4. 建立设计基线

至少明确：

- 背景、目标、非目标
- 本次范围和影响范围
- 可复用的现有能力
- 高成本契约
- 必要的边界、风险和确认项

然后按任务实际需要设计：

- Flow / 状态
- Data / DB
- API / 交互契约
- 系统集成
- 数据迁移
- 技术结构调整
- 其他真正影响实现的关键设计

不要先给任务套 A/B/C/D/E 等固定类型标签；直接根据当前任务实际涉及的设计维度选择内容。

普通业务功能默认优先覆盖：

> **Flow + Data/DB + API**

### 5. 定义验收与验证

把用户真正可验收的结果写成稳定的验收项，使用 `AC01`、`AC02` 等 ID。

每个 AC 至少说明：

- 要验收什么
- 用什么方式验证
- 什么结果算通过

AC 描述“结果是否成立”，不要写成 Controller / Service / Mapper 等代码任务。

能由工具稳定判定的规则，优先使用确定性检查；具体方法见任务设计规范。

不要为了填表制造测试或工具。

### 6. 做设计检查

完成前检查：

- 目标、范围和方案是否一致
- 关键流程、状态、数据和接口是否闭合
- 关键动作是否有明确的数据或系统落点
- 权限、异常、幂等、并发、兼容性是否遗漏
- 是否复用了项目已有能力
- 是否无必要增加新表、新接口、新抽象
- 是否把未知业务规则当成事实
- 高风险契约是否有明确验证方式

未确认信息不要自行编造，并分成两类：

- **阻塞确认项**：会改变核心业务行为或高成本契约；未解决前禁止实施。
- **非阻塞待确认项**：不影响当前高成本契约，可按项目现有约定或低成本实现细节继续收敛。

## 多 Agent 设计协作

- 默认一个 Builder 维护唯一 `design.md`，完成自查后再交给一个只读 Design Reviewer；独立评审不可用时降级 same-context，并记录实际模式。
- 默认只委派一层，Reviewer 自己完成审查，不再创建 Explore / Task / Agent 或 Paseo 子代理。确有较大的独立分析范围且收益明确时，由主 Agent 先确定责任范围和总并发预算；原生子代理与 Paseo 子代理都计入预算。禁止多人同时修改设计文档。
- Reviewer / 只读分析代理的委派提示必须明确只读、默认禁止继续委派、审查或分析范围、当前轮次（审查时）与输出要求，不能假定受托代理已加载本 Skill。
- 复审优先复用同一个 Reviewer。只有上下文丢失、不可用或范围明显变化时才替换，并移交必要设计、改动和未闭合 findings；不能以重新创建代理代替缩小审查范围。
- 支持完成通知时异步等待，不用 ping / sleep 空等或反复轮询。用户可覆盖本次并行偏好；设计确认和权限边界仍按已获授权执行。

## 设计审查与人工确认闸门

设计阶段有两道顺序固定的门：

```text
AI 起草 design.md
  → 对抗式 Design Review（优先独立）
  → AI 根据 finding 修订
  → Review PASS
  → 阻塞确认项清零
  → 用户确认设计
```

无论用户最初说的是“先设计”还是“实现 / 开发 / 完成这个功能”，只要当前任务触发了 `task-design`：

1. 新建设计或实质变更高成本契约时，更新 `design.md` 并标记以下状态；纯澄清和恢复已有任务保留有效审查、确认依据与轮次，不重复开门：
   - `设计审查：待审查`
   - `设计确认：待确认`
   - `设计版本：v1`（已有设计沿用当前版本；高成本契约实质变化时递增，纯澄清不递增）
   - `设计确认依据：无`
   - `设计审查轮次：0/3`（恢复已有任务时沿用计数）
2. 完成 Builder 自查后启动一个 Reviewer，优先 independent，不可用时降级 same-context。Reviewer **只找问题，不直接改设计**，遵守上述委派预算；记录实际审查模式和轮次。
3. 首轮完整检查当前任务的设计与必要的现有实现；后续增量复审核对阻塞 findings、对应修订及受影响契约，不默认重读全仓库或重做全部审查。只有范围或关键不变量实质变化时扩大到受影响的完整链路。重点检查：
   - 目标 / 范围是否误解或漏场景
   - Flow / 状态是否有非法流转、失败态、恢复态遗漏
   - Data / DB 是否有不必要结构、唯一性 / 历史 / 存量兼容问题
   - API / 集成是否重复建设、泄漏内部实现、缺少超时 / 重试 / 幂等 / 补偿
   - 权限、并发、事务、兼容边界是否闭合
   - 是否存在明显过度设计

   完成约定范围后集中报告本轮结论、已发现的阻塞项及证据，避免每发现一项就驱动一次返工。复审仍应报告新发现的真实风险，不受旧 findings 清单限制。

4. Finding 分级：
   - `Critical / High`：阻塞设计确认
   - `Medium / Low`：记录，不默认返工或阻塞

   每条阻塞 finding 应说明具体场景、证据、违反的目标 / 契约和实际影响；纯优化建议、措辞偏好和未经支持的假设不能升级为 High。

5. 如果 Review FAIL：
   - Builder 集中修订本轮 Critical / High findings，完成自查后一次性提交修订摘要、对应位置和待复核项；
   - 由原 Reviewer 做增量复审，记录各 finding 闭合情况及新增阻塞项；
   - 每个设计审查阶段默认最多 3 轮，包含首审和全部追加确认，即首审 + 最多两次复审。
6. Review PASS 条件：
   - Critical = 0
   - High = 0
   - 关键高成本契约闭合
   - 重大未知已正确区分为阻塞确认项 / 非阻塞待确认项
   - 关键 AC 与验证方式足够
7. PASS 后将 `设计审查` 标为 `PASS`，停止主动完善和追加确认。Medium / Low 留作非阻塞说明，不为清零观察项主动改设计再开一轮。用户要求进一步修改或出现新的真实阻塞证据时，才审查受影响范围，并计入轮次。
8. 如果仍有**阻塞确认项**：先把这些决策交给用户，不进入总体设计确认；用户给出选择后更新 `design.md`，将设计审查重置为 `待审查`，重新 Review。
9. 只有 `阻塞确认项 = 0` 时，才向用户请求总体设计确认。
10. **停止，不生成执行任务、不开始编码。**
11. 只有收到用户对**当前已审阅设计版本**的无条件明确确认（如“确认”“按这个做”“可以实施”）后，才将 `设计确认` 改为 `已确认`，并记录可追溯的用户确认依据和对应设计版本。不能仅凭文档中旧的 `已确认` 状态推断授权。
12. 如果用户的“确认”同时附带任何会改变高成本契约的条件或修改（例如“可以，但状态 X 改成 Y”），这不算已确认：先更新设计版本，清空旧确认依据，重置 Review，再走一轮审查和确认。

同一目标下，技术修正、递增版本、换 Reviewer 或新会话都不重置轮次。只有用户实质改变目标或高成本契约，才记录变更依据并为受影响范围开始新的审查阶段；不能通过自行扩展设计无限重启。

用户明确要求继续审查或指定轮数时，可按该指令调整上限并保留累计记录；Agent 不得自行突破默认上限。

第 3 轮设计审查仍 FAIL 时，停止自动循环，报告剩余阻塞 findings、证据和待决策点，不把未成熟设计包装成“待确认方案”。设计与实现分别计数，恢复会话时保留已用轮次。

这道人工闸门只确认高成本设计，不要求用户确认 Controller / Service / SQL / DTO 等低成本实现细节。

### 实现中发现设计需要变化

先区分“实现未满足已确认契约”与“已确认契约需要改变”。修复以满足原契约、纯文字澄清或内部实现调整，不重置已有设计确认，也不重启设计审查；在实现审查中复核受影响范围即可。

如果实现过程中发现以下高成本契约本身必须改变：

- 核心业务流程 / 状态
- DB Schema / 核心数据模型
- 公共 / 外部 API
- 权限边界
- 消息 / 事件契约
- 数据迁移 / 兼容策略
- 并发、幂等、事务边界

必须：

1. 更新 `design.md`；
2. 递增设计版本，清空旧确认依据，将 `设计审查` 重新标为 `待审查`、`设计确认` 重新标为 `待确认`；
3. 暂停受影响的实现；
4. 对变化及受影响契约执行设计审查（优先复用 Reviewer，不可用则 same-context 并记录模式）；轮次按上述规则累计；
5. Review PASS 且阻塞确认项清零后，再交给用户重新确认；
6. 用户确认后继续。

低成本实现细节无需回填设计文档，也无需再次找用户确认。

除设计确认外，只有以下情况才额外中断并找用户：

- 缺失的业务规则会改变核心行为；
- 存在多个不可兼容方案且无法从项目现状判断；
- 需要用户凭据、授权或不可逆外部操作；
- 继续执行可能造成数据破坏或越权。

## 完成条件

- 已创建或更新唯一主设计文档 `design.md`
- 设计深度与任务风险匹配
- 高成本契约已经明确；未决信息已区分阻塞确认项 / 非阻塞待确认项
- 已检查项目规则和现有实现
- 已说明关键边界、风险、AC 与验证方式
- 没有为低成本实现细节做过度设计
- 没有混入动态任务进度和返工状态
- 已明确 `设计审查` 状态（`待审查` / `PASS`）
- 已记录 `审查模式`（`independent` / `same-context`）
- 已明确 `设计确认` 状态（`待确认` / `已确认`）；若已确认，记录可追溯的用户确认依据和对应设计版本
- 人工确认前对抗式设计审查已 PASS
- 进入实施前阻塞确认项 = 0
- `design.md` 足以作为后续实现的稳定基线

## 与其他 Skill 的关系

- **task-design**：决定“要不要设计、设计什么、设计到什么程度”。
- **work-convention**：决定“设计和执行资料放哪里、如何维护生命周期”。
- **task-execution**：把目标 / `design.md` 转成 `tasks.md`，并持续实现、验证和推进。

设计内容以 `task-design` 为准；执行状态以 `tasks.md` 为准。

## 回复约定

Design Review PASS 后再请求人工确认：

```text
已创建/更新：<design.md 路径>
设计审查：PASS
审查模式：independent | same-context
设计确认：待确认
设计基线：<核心设计摘要>
关键取舍：<需要用户重点看的内容>
阻塞确认项：无
非阻塞待确认项：<有则列出；没有则写无>
下一步：请确认设计；确认后再自动拆 tasks 并实施
```

收到用户对当前设计版本的明确确认后，记录确认依据及设计版本，将 `设计确认` 更新为 `已确认`。如果用户原始目标包含实现，则继续进入 `task-execution`，后续无需逐任务确认。
