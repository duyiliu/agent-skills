# Design Review 生命周期

仅在 Design Review 返工、恢复或高成本契约变化时读取。正常首轮设计无需加载本文全部细节。

## 状态

新设计阶段：

- 设计审查：待审查
- 设计确认：待确认
- 设计版本：v1
- 设计确认依据：无
- 设计审查轮次：0/3
- 设计审查范围与结论：无

高成本契约变化时：

- 递增设计版本；
- 清空旧确认依据；
- 仅使受影响的审查范围失效，未受影响覆盖继续有效；
- 审查与确认重置为待处理；
- 技术返工、换 Reviewer、新会话不重置当前阶段轮次。

只有用户实质改变目标或高成本契约，才为受影响范围开始新的审查阶段并重置该阶段轮次。

## Reviewer

- 默认一个 Builder + 一个只读 Reviewer。
- Reviewer 优先独立上下文；不可用时 same-context。
- 复审优先复用原 Reviewer；只有不可用、上下文丢失或范围明显变化时替换。
- 默认只委派一层，不让 Reviewer 再递归创建子代理。
- 禁止多个执行者同时修改同一份设计文档。

记录实际审查模式和累计有效审查范围；未列明的范围不视为已审查。

## 首审

重点攻击：

- 目标 / 范围是否误解或漏场景；
- Flow / 状态是否缺失败态、恢复态或非法流转；
- Data / DB 是否有唯一性、历史数据、存量兼容问题；
- API / 集成是否重复建设或缺超时、重试、幂等、补偿；
- 权限、并发、事务、兼容边界是否闭合；
- 是否明显过度设计。

每个阻塞 finding 必须包含具体场景、证据、违反的目标 / 契约和实际影响。措辞偏好、纯优化建议、未经支持的假设不能升级为 High。

## FAIL 与复审

每轮集中处理全部 Critical / High，不要发现一条就返工一次。

FAIL 后：

1. Builder 集中修复本轮阻塞 findings；
2. 完成自查并提供修订摘要；
3. 原 Reviewer 做增量复审；
4. 复审只核对未闭合 finding、修订和受影响链路；关键不变量变化时才扩大范围。

默认最多 3 轮，包含首审。第 3 轮仍 FAIL 时停止自动循环，保留剩余 findings、证据和待决策点。

用户明确要求继续审查或指定轮数时可覆盖默认上限，但 Agent 不自行突破。

## PASS

PASS 条件：

- Critical = 0；
- High = 0；
- 关键高成本契约闭合；
- 阻塞 / 非阻塞未知已正确区分；
- 关键 AC 与验证方式足够。

PASS 后停止主动完善。Medium / Low 只做非阻塞说明。

如果用户已经明确收敛到某方案，后续低成本增量只核对落地一致性，不重复完整方案推演。

## 人工确认

只有阻塞确认项清零后才请求总体确认。

确认必须对应当前已审阅设计版本。旧文档里的“已确认”状态本身不能代替用户授权。

如果用户在确认时增加会改变高成本契约的条件：

1. 更新设计；
2. 递增版本；
3. 使受影响确认和审查范围失效；
4. 重新 Review；
5. PASS 后再次确认。

## 实现阶段回流

实现中仅当高成本契约本身必须变化时回流：

1. 更新 \`design.md\`；
2. 暂停受影响任务；
3. 审查受影响契约；
4. PASS 且阻塞确认项清零；
5. 用户重新确认；
6. 返回 \`task-execution\`。

“实现不符合原设计”不是设计变化，直接修实现。
