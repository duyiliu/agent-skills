# 任务设计规范

> 目标：让日常研发任务在“足够设计”和“不过度设计”之间取得平衡。
>
> 核心原则：**高成本契约前置，低成本实现细节渐进。**

## 1. 什么值得先设计

设计不是按任务大小决定，而是按**修改成本和契约风险**决定。

以下内容一旦被其他模块、数据、用户或外部系统依赖，后续修改成本较高，应优先在实现前明确：

- 核心业务流程与状态
- 数据库 Schema 和核心数据模型
- 公共 / 外部 API
- 权限和安全边界
- 消息 / 事件契约
- 数据迁移与兼容策略
- 跨系统调用关系
- 并发、幂等、事务边界
- 难回滚的技术切换

以下内容通常可以在实现中收敛：

- Service 拆几个类
- DTO / VO 的内部组织
- 私有方法抽象
- SQL 的具体写法
- 局部类层次
- 尚无真实需求的扩展点

原则：

> **越不可逆、越跨边界、越多人依赖，越应该先设计。**

## 2. design.md 的定位

`design.md` 是当前任务的**设计基线**，不是完整规格书，也不是一次性冻结的最终真理。

它应该做到：

- 让开发知道要实现什么
- 让前后端 / 测试 / 相关系统理解同一套契约
- 让后续会话快速恢复关键上下文
- 在实现发现真实偏差时可以被更新

普通任务默认一个 `design.md`。

只有内容明显膨胀、影响主文档可读性时，才按项目或 `work-convention` 拆补充文档。

## 3. 常见任务的设计重点

以下内容只是常见场景的参考，不是一套必须执行的任务分类体系。

不要先把任务标成 A/B/C/D/E，也不要为了归类而拆分设计。真实任务往往同时包含业务流程、数据、接口、系统集成、迁移或技术结构中的多个方面，应直接选择当前任务真正需要的设计内容。

### 业务功能

典型：审核、退款、预约、患者/客户管理、订单能力、后台业务模块。

默认重点：

- **Flow**：业务对象、流程、状态、关键异常
- **Data / DB**：数据模型、表、关系、约束、索引
- **API**：接口契约、权限、主要错误
- 必要的幂等、并发、兼容边界

普通业务功能默认形成：

> **Flow + Data/DB + API**

### 系统集成

典型：支付、短信、AI 服务、第三方 HIS、MQ、外部平台。

默认重点：

- 参与方和调用链路
- 请求 / 回调 / 消息契约
- 认证、配置和环境差异
- 超时、重试、幂等、补偿
- 失败路径和降级
- 可观测性与联调验证

推荐用时序图表达关键链路。

### 数据变更

典型：Schema 调整、历史数据迁移、字段重构、主数据整合。

默认重点：

- 数据来源与目标
- Schema / 字段映射
- 迁移或回填步骤
- 新旧数据兼容
- 校验方式
- 回滚 / 恢复策略

存在生产存量数据时，迁移和校验通常比 DDL 本身更重要。

### 技术改造

典型：权限体系重构、缓存改造、模块拆分、基础组件替换。

默认重点：

- 当前问题和现状
- 目标结构
- 影响模块和边界
- 迁移 / 切换路径
- 向后兼容
- 风险、回滚和验证

不要把“技术改造”写成文件修改清单，应描述结构变化和迁移边界。

### 混合任务

真实任务可以同时包含多个方面。

例如“新增退款功能并接第三方支付”同时需要：

- 退款状态、DB、API
- 支付调用、回调、重试、幂等

此时仍使用一个 `design.md`，合并真正需要的设计内容，不创建两套设计。

## 4. 设计深度

设计深度按风险调整。

### 轻量

适合边界清楚、复用现有模式的小功能：

- 目标 / 范围
- 简要 Flow
- 数据或 API 变化
- 风险 / 确认项

### 标准

适合大多数完整业务功能：

- Flow + 状态
- Data / DB
- API
- 权限 / 异常
- 必要的幂等 / 兼容
- 验证方式

### 深度

只有确有风险时增加：

- 权限矩阵
- 状态机
- 多系统时序图
- 数据迁移与回滚
- 事件流
- 并发控制
- 超时 / 重试 / 补偿
- 灰度 / 双写 / 切换方案

不要为了文档完整而自动升级设计深度。

## 5. 验收与验证

设计文档不仅要描述“正确结果是什么”，还应尽量说明“如何判断它正确”。

对用户真正可验收的结果使用稳定 ID（`AC01`、`AC02`…）。后续 `task-execution` 用这些 ID 检查设计是否被任务和最终验证完整覆盖。

每个关键 AC 至少明确：

1. **验收结果**：要证明什么。
2. **验证方式**：用什么检查。
3. **通过标准**：什么结果算成功。

能由工具稳定判定的规则，优先使用确定性检查，例如：

| 设计契约 | 优先验证方式 |
|---|---|
| 状态只能合法流转 | 单元测试 / 状态机测试 |
| 数据不能重复 | 唯一约束 + 测试 |
| API 权限正确 | API / 集成测试 |
| 请求响应契约稳定 | Contract / 场景测试 |
| 模块依赖方向正确 | 架构依赖检查 |
| 类型和基本静态规则 | typecheck / lint / 编译 |
| 数据迁移正确 | 校验 SQL / 对账脚本 / 迁移测试 |
| 完整业务链路 | 场景测试 / E2E |

高风险场景可按需使用 mutation testing 等更强验证手段，但不是日常默认要求。

原则：

> **能机器判对错的规则，尽量交给工具；不要只靠 Prompt 或 Agent 自我检查。**

设计阶段不要求提前写完所有测试代码，只需要把真正关键的验证方式定义清楚。

## 6. 设计与实现边界

设计阶段应明确：

- 已确定的业务和技术契约
- 不能轻易修改的边界
- 风险
- 稳定的 AC 验收项
- 阻塞确认项：会改变核心行为 / 高成本契约，未解决前禁止实施
- 非阻塞待确认项：不影响当前高成本契约，可在实现中按项目约定收敛
- 关键验证方式

不要提前设计：

- 类和私有方法的最终结构
- 内部 DTO 的所有细节
- SQL 的最终写法
- 没有真实需求支撑的扩展点

后续实现发现设计假设错误时，应更新 `design.md` 中受影响的高成本契约，不保留已经失效的“双份真相”。

## 7. 最终原则

> **先设计真正昂贵的东西，不提前设计便宜的东西。**
>
> **确定的契约先明确，不确定的实现边做边收敛。**
>
> **一个任务默认一个 design.md，复杂点在哪里就补哪里。**
>
> **关键契约不仅要写清楚，还要形成可追踪的 AC，并尽量定义可判定的验证方式。**
