# Implementation Review 生命周期

仅在实现审查返工、恢复、风险降级或复杂范围继承时读取。正常 PASS 路径无需加载本文全部细节。

## Reviewer 与并行

- 默认单 Builder + 一个只读 Reviewer。
- 首审优先独立上下文；不可用时 same-context。
- 复审优先复用原 Reviewer；不可用、上下文丢失或范围明显变化时才替换。
- Reviewer 默认不再递归委派。
- 并行实施必须读写范围互不冲突、依赖已满足且可分别验证；主 Agent 负责集成验证。
- 子 Agent 的“已完成”不能代替真实代码和验证证据。

## 审查模式

记录：

- `independent`
- `same-context`
- `按风险分层跳过（依据）`

高风险改动包括：

- 核心流程 / 状态机；
- DB Schema / 核心数据；
- 公共 / 外部 API；
- 权限；
- 消息 / 事件；
- 迁移 / 兼容；
- 并发 / 幂等 / 事务。

高风险不可跳过，只能在独立 Reviewer 不可用时降级 same-context。

低风险同时满足以下条件时，用户可明确同意 further downgrade / skip：

- 纯新增；
- 有完整可复跑验证；
- 不改变既有链路；
- 不属于任何高风险类别。

未明确属于低风险的，按高风险处理。

## 首审范围

Reviewer 读取：

- 已确认的 `design.md`（若有）；
- `tasks.md`；
- 代码基线；
- 本次 diff，包括新增未跟踪文件；
- 真实构建 / 测试 / 验收证据。

默认增量核验：

- 设计契约落地一致性；
- 验证证据真实性；
- 范围污染和回归影响。

已在 Design Review 中完整推演且有记录的上游设计范围，不在 Implementation Review 重做一遍；未记录覆盖的范围仍按需检查。

## Finding

分级：

- Critical / High：阻塞交付；
- Medium / Low：记录，不默认阻塞。

阻塞 finding 应包含：

- 具体场景；
- 证据位置；
- 违反的 design / AC；
- 实际影响。

纯优化、措辞偏好、无证据假设不能升级为 High。

## FAIL 与返工

每轮集中处理阻塞 findings。

FAIL 后：

1. 将 Critical / High 转成 `R01`、`R02` 等返工任务；
2. Builder 集中修复并执行必要验证；
3. 提供修订摘要和证据；
4. 原 Reviewer 做增量复审；
5. 只检查修复、未闭合 finding 和受影响链路；关键不变量变化时才扩大范围。

默认最多 3 轮，包含首审。技术返工、版本递增、换 Reviewer、新会话都不重置当前阶段计数。只有用户实质改变目标或高成本契约，才为受影响范围开始新阶段。

第 3 轮仍 FAIL 时停止自动循环，标记 `blocked` 并保留剩余 findings 和证据。

## PASS

PASS 条件：

- Critical = 0；
- High = 0；
- design AC 已映射到实现与证据；
- 已授权范围内的关键确定性验证通过；
- 没有证据表明实现违反明确契约或验收标准。

PASS 后停止主动修改。Medium / Low 作为非阻塞遗留说明。

## 证据边界

- 不默认重复已有可靠全量构建 / 测试，除非代码变化影响它、结果过期或存在具体疑点。
- 静态核对、编译、运行时验收分别记录。
- 待环境验收保持真实状态；更多 AI Review 不能把“未验收”变成“已通过”。
- Reviewer 可以抽查证据，但不能把 Builder 的自报当作证据。

## 恢复

恢复时保留：

- 当前 Review 阶段；
- 已用轮次；
- Reviewer；
- 未闭合 findings；
- 已验证证据与待环境验收项。

已有 PASS 且代码和范围未变化时，不重新首审。
