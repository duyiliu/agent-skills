# Task Execution

## 目标

让日常研发从“AI 帮我做一步”变成：

```text
用户给目标
  → 必要时 task-design
  → 设计 Review PASS（优先独立）
  → 用户确认 design.md
  → 生成 tasks.md
  → Agent 连续实现并验证
  → 实现 Review（优先独立）
  → 集中修复阻塞 findings，增量复审
  → PASS 后交付，明确环境验收证据边界
```

默认**只在设计阶段设置人工确认闸门**；设计确认后，不要求用户逐任务确认，除非出现新的高成本设计变更或真正阻塞。

**路由优先级：按交付性质而非步骤多少选主 Skill。** 既有契约下的 Bug 修复、纯调查、行为不变重构、指标型性能优化分别由 `goal-fix / goal-investigate / goal-refactor / goal-performance` 负责，即使涉及多轮也不自动切成本 Skill。需要稳定设计基线的高成本契约变更先走 `task-design`；本 Skill 负责已确认设计下的工程交付。

## 启动前

先读取：

- 项目规则：`AGENTS.md`、`CLAUDE.md`、rules、README
- 与目标相关的现有实现
- 已有 `work/任务/<任务名>/design.md`、`tasks.md`
- 可用时读取 `work-convention`
- 如果任务符合 `task-design` 的触发条件，先建立或更新 `design.md`

如果任务触发了 `task-design`：

- `设计审查 != PASS` → **禁止进入执行**，返回 `task-design` 完成其内置的设计对抗审查；
- `阻塞确认项 != 0` → **禁止进入执行**，先由用户做必要决策并回到 `task-design` 更新、复审；
- `设计审查 = PASS` 且 `设计确认 = 待确认` → **停止执行并等待用户确认**；
- 只有同时满足 `设计审查 = PASS`、`阻塞确认项 = 0`、`设计确认 = 已确认`，且有可追溯的用户确认依据对应**当前设计版本**，才允许创建 `tasks.md` 和修改业务代码；状态字段本身不能代替用户授权；
- 用户若在“确认”时附带会改变高成本契约的条件，不视为已确认：先更新设计并重新 Review。

如果用户只是要求设计，不进入本 Skill。

## tasks.md

需要持续状态时创建：

```text
work/任务/<任务名>/tasks.md
```

没有 `design.md` 也可以存在 `tasks.md`；但任务涉及高成本契约时不能用任务清单替代设计。

创建时读取 `templates/tasks-template.md`。

### 建立代码基线

在修改业务代码前，尽量记录：

- 当前 branch
- 当前 HEAD / start commit
- 任务开始前已经存在的工作区修改（至少记录文件范围；无法可靠识别时明确写“未知”）

Git 不可用时不因此阻塞普通开发，但要明确基线不可得。

**不得为了让 diff 干净而 reset / checkout / revert 用户在任务开始前已有的修改。**

`task-execution` 本身不隐含 `commit`、`push`、`deploy/release`、生产环境写入或不可逆外部操作权限。只有项目规则已经明确允许，或用户明确授权时，才执行这些动作。

### 拆分原则

按**可独立交付、可独立验证的能力单元**拆，不按代码层拆。

好：

- “完成退款申请入口并保证重复请求幂等”
- “接通支付回调并覆盖成功/失败状态流转”
- “迁移历史字段并验证新旧数据一致”

不好：

- “写 Controller”
- “写 Service”
- “写 Mapper”
- “补几个 DTO”

默认只规划足够支撑当前目标的一层任务，不提前把所有代码细节拆到几十项。

每个任务至少包含：

- 目标
- 依赖
- 对应验收（有 `design.md` 时引用 `ACxx`）
- 验收标准
- 验证方式
- 状态

### AC 覆盖检查

有 `design.md` 时，开始实现前必须检查：

- 每个 `ACxx` 至少被一个 Task 或“最终核验”覆盖；
- 任务中的验收不能与 design 的 AC 相冲突；
- 允许存在支撑性任务没有直接 AC，但必须服务于被覆盖的能力，不能借机扩 scope。

发现 AC 漏覆盖时直接补齐 `tasks.md`，不需要因此打断用户。

## 执行状态

只使用：

- `pending`
- `in_progress`
- `blocked`
- `done`

同一时刻默认只有一个 `in_progress` 任务；满足下述安全并行条件时才允许多个互不依赖的任务同时处于 `in_progress`。

状态只写在 `tasks.md`，不要同步复制到 `design.md`。

## 多 Agent 执行策略

- **默认单 Builder 串行执行，完成自查后交给一个只读 Reviewer**。只有任务依赖已满足、读写范围互不冲突、可以分别验证且收益大于协调成本时，才委派额外实施或分析。
- 默认只委派一层，Reviewer 不再创建 Explore / Task / Agent 或 Paseo 子代理。确需额外委派时，由主 Agent 先确定总并发预算、执行者和读写范围并记录在 `tasks.md`；原生子代理与 Paseo 子代理都计入预算。禁止多人同时修改相同文件、共享状态或迁移目标。
- Reviewer / 只读分析代理的委派提示必须明确只读、默认禁止继续委派、审查或分析范围、当前轮次（审查时）与输出要求，不能假定受托代理已加载本 Skill。
- 实施代理的提示应明确目标、允许写入的文件 / 模块、禁止修改的范围、必要验证和输出要求；不套用只读约束，默认不得继续委派或回退他人的改动。
- 主 Agent 负责状态协调、合并冲突处理、集成验证和最终交付；不能用子 Agent 的“已完成”代替真实验证。
- 首审优先独立上下文；复审复用原 Reviewer，只在不可用、上下文丢失或范围明显变化时替换。运行器不支持子 Agent 时使用 same-context 审查，不额外引入编排工具。
- 支持完成通知时异步等待，不用 ping / sleep 空等或反复轮询。用户提示词可以覆盖本次并行偏好；设计确认、权限和数据安全边界仍按已获授权执行。

## 主循环

### 1. 选择任务

默认选择第一个依赖已满足的 `pending` 任务，标为 `in_progress`。只有符合“多 Agent 执行策略”的独立任务才可并行启动，并分别维护状态和验证证据。

### 2. 实现

先读相关代码，再修改。

实现过程允许调整低成本细节；不要因为最初计划写得不够细就停下来问用户。

### 3. 验证

在用户授权和项目约束内，执行该任务声明的必要确定性验证，例如：

- 编译 / typecheck
- 单元测试
- API / 场景测试
- 数据库约束 / 校验 SQL
- lint / 架构检查
- 现有项目已有的验收命令

记录命令、结果 / 退出码、日志位置和对应代码版本；未提交代码可用关键文件哈希或时间戳标识。不能只根据“代码看起来对”把任务标为完成。

已有对应当前代码的可靠结果时复用证据；只有代码变化影响检查、证据缺失 / 过期、出现新失败或有具体疑点时才补跑。Reviewer 核对真实证据，不默认重复全量构建或测试。

静态核对、编译通过与运行时验收分别记录。未获授权或环境不可用的验收项标为“待环境验收”，不能用额外 AI 审查替代。若用户本次只要求实现和静态交付，可在该边界完成并列出待验收项；若本次目标包含实测结果，相关任务保持 pending / blocked，不宣称整个目标完成。

### 4. 处理失败

验证失败时：

1. 保持 `in_progress`；
2. 根据实际错误诊断；
3. 修复；
4. 重新验证。

如果连续多次失败但没有获得新的证据，默认第三次后停止盲目重试，记录根因和已尝试方案并标为 `blocked`。

### 5. 处理设计偏差

修复实现以满足原先已确认的契约，不属于设计变更；纯澄清或内部实现调整不重置确认，按实现审查复核即可。

如果实现发现：

- 核心流程
- DB Schema / 核心数据
- 公共 API
- 权限
- 消息契约
- 迁移 / 兼容
- 并发 / 幂等 / 事务

等已确认的高成本契约本身需要改变：

1. 更新 `design.md`；
2. 递增设计版本，清空旧确认依据，将 `设计审查` 重新标为 `待审查`、`设计确认` 重新标为 `待确认`；
3. 暂停受影响任务；
4. 回到 `task-design`，审查变化及受影响契约，优先复用原 Reviewer；技术返工和版本递增不重置轮次；
5. Review PASS、阻塞确认项清零后等待用户重新确认；
6. 再调整受影响的 tasks 和 AC 覆盖关系并继续实现。

低成本实现细节变化不回填设计，也不触发人工确认。

### 6. 完成任务

只有验收条件满足且验证通过后才标记 `done`，并记录必要的验证证据摘要。

然后自动进入下一个可执行任务。

## 什么时候找用户

默认不因为以下事情中断：

- 类怎么拆
- 方法怎么命名
- SQL 怎么写
- DTO 怎么组织
- 选用项目中已有的哪种同类实现模式

只有以下情况才进入 `blocked` 并找用户：

- 缺失业务规则会改变核心行为；
- 两个不可兼容方案都合理，且项目现状无法判断；
- 需要账号、凭据、授权或用户侧操作；
- 涉及不可逆外部动作、生产数据或明显安全风险；
- 环境本身不可用，Agent 无法继续验证。

## 对抗式实现审查闸门

本次实现和已获授权的必要验证完成后，进行实现审查再交付。待环境验收项保持真实状态，不因更多审查而视为已验证。

本 Skill 自己负责启动 Reviewer；不依赖额外 Review Skill。

审查强度按改动风险分层：

- 高风险改动（核心流程 / 状态机、数据迁移、公共契约、权限、并发与事务边界）保留完整独立审查；
- 低风险改动（纯新增、有完整可复跑验证覆盖、不改动既有链路）默认按下方「默认增量核验范围」执行，经用户明确同意可进一步降级为 same-context 核验或跳过独立审查；跳过后在 `tasks.md` 将 `实现审查模式` 记为 `按风险分层跳过`，并附同意依据与覆盖范围。

Reviewer 规则：

- 首轮优先使用一个独立 subagent / 独立上下文，遵守上述委派预算；
- 当前环境不支持独立 Reviewer 时，允许降级为 same-context 对抗审查；
- 无论使用哪种模式，都必须在 `tasks.md` 记录 `实现审查模式：independent | same-context | 按风险分层跳过（依据）`，不能把 same-context 伪装成独立审查，也不能在未记录依据的情况下记为跳过；
- 核对真实代码和构建 / 测试证据，不把 Builder 的自报结果当成证据，也不默认重复已有可靠检查；
- **默认增量核验范围**：审查对象 = design 契约的落地一致性、验证证据真实性、范围污染与回归影响；**不重复设计审查已完成的原型 / 上游对照与契约推演**（边界 = `design.md` 的「设计审查范围与结论」；该记录未列明的范围不视为已审查，仍按需核验）；验证证据以抽查核验为主，全量重跑场景 / 构建仅在有具体疑点或用户明确要求时进行；
- **只找问题，不直接修改业务代码**；
- 首轮读取已确认的 `design.md`、`tasks.md`、代码基线、本次代码 / Git diff（含新增未跟踪文件）和真实验证结果，区分本任务变化与任务前已有变化；
- 复审输入为本轮变更摘要、相关代码、待闭合 findings 和验证证据，只检查修复及受影响链路。只有范围或关键不变量实质变化时扩大审查，不默认重读全仓库；
- 尝试推翻“实现已经满足设计和验收标准，可以交付”。

完成约定范围后集中提交本轮结论、阻塞 findings 和证据，避免逐条报告触发多次返工。增量复审也应报告新发现的真实风险，不受旧 findings 清单限制。

重点攻击：

- design 契约、AC 与真实实现是否一致
- 非法状态、空值、重复请求、失败路径
- 权限绕过、幂等、并发、事务与部分成功
- 旧数据 / 旧接口兼容
- 外部依赖异常、超时、重试
- 回归和范围污染
- 测试是否假阳性、只覆盖快乐路径、或结果不是基于当前代码

Finding 分级：

- `Critical / High`：阻塞交付
- `Medium / Low`：记录，不默认返工或阻塞

每条阻塞 finding 应包含具体场景、证据位置、违反的 design / 验收标准和实际影响。纯优化建议、措辞偏好和未经支持的假设不能升级为 High。

如果审查 `FAIL`：

1. 把 Critical / High finding 转成新的返工任务（如 `R01`、`R02`）追加到 `tasks.md`；
2. Builder 集中修复本轮阻塞 findings，完成必要验证后一次性提交修订摘要与证据；
3. 原 Reviewer 做增量复审，记录逐项闭合情况、新增阻塞项和本轮范围；不可用时允许 same-context 并明确记录。

Review PASS 条件：

- Critical = 0
- High = 0
- design 的所有 AC 已映射到实现与验证项，证据层级、已验证 / 待环境验收状态真实可追溯
- 本次交付范围内已获授权的关键确定性验证通过
- 没有证据表明实现违反 design 或明确验收标准

审查 PASS 表示在所列范围和证据下未发现阻塞级问题，不等于未执行的运行时验收已通过。

每个实现审查阶段默认最多 3 轮，包含首审和全部追加确认，即首审 + 最多两次复审；在 `tasks.md` 记录轮次、Reviewer、审查范围和结论。技术返工、版本递增、换 Reviewer 或恢复会话都不重置计数。只有用户实质改变目标或高成本契约，才记录依据并为受影响范围开始新阶段。第 3 轮仍 FAIL 时停止自动循环，标记 `blocked` 并保留剩余 findings 和证据。

用户明确要求继续审查或指定轮数时，可按该指令调整上限并保留累计记录；Agent 不得自行突破默认上限。

**PASS 后停止主动修改和追加确认，进入交付。** Medium / Low 留作非阻塞说明，不为清零观察项主动修改代码再开一轮。用户要求后续修改或出现新的真实阻塞证据时，只复核受影响范围，并计入轮次；关键不变量变化时相应扩大范围。

## 完成条件

只有同时满足才完成：

- 所有本次范围内的实现和返工任务均为 `done`，且没有未解决的 `blocked` 任务或阻塞项
- 有 design 时所有 AC 已被 Task / 最终核验覆盖，证据与待环境验收项逐项列明
- 本次已授权交付边界内的关键确定性验证和必要构建 / 测试通过
- 对抗式实现审查最终 `PASS`（或按风险分层经用户同意跳过并记录依据），且已记录审查模式
- Critical / High findings 为 0
- `tasks.md` 已更新为最终状态

代码交付完成但环境验收未执行时，明确报告“实现完成，环境验收待执行”，不能报告功能已实测通过。用户目标要求的运行时验证尚未完成时，整体任务仍未完成。

## 中断与恢复

新的 Agent / 新会话恢复任务时：

1. 读项目规则；
2. 读 `design.md`（若存在）；
3. 读 `tasks.md`；
4. 核对 tasks.md 记录的 branch / start commit / 既有工作区修改；
5. 核对当前代码和 Git diff，区分本任务修改与任务前已有修改；
6. 不信任旧的 `in_progress` 自报状态，先验证真实代码；
7. 恢复审查轮次、Reviewer 和未闭合 findings，不重新首审或清零计数；
8. 从第一个真实未完成且可执行的任务继续。已有 PASS 且范围与代码未变时直接完成剩余交付。

文件用于**恢复状态**，不代表 Claude Code / Codex 进程退出后会自己重新启动。

需要“进程挂了自动拉起、跨机器无人值守、定时继续、多个执行器并行”时，再由 Hermes / 外部 orchestrator 调度；它仍然可以复用同一套 `design.md + tasks.md` 协议。

## 回复约定

全部完成后再向用户做一次交付汇报：

```text
已完成：<目标>
设计：<design.md 或无>
执行：<tasks.md 或直接完成>
验证：<关键检查>
实现审查：PASS（independent | same-context）| 按风险分层跳过（依据）
AC 覆盖：<实现覆盖与证据层级 / 无 design>
环境验收：<已通过 / 待执行及范围 / 不适用>
遗留：<Medium/Low 或无>
```

存在 `blocked` 时只能报告部分完成、未完成任务及真正阻塞继续执行的信息，不得宣称整体交付完成；不把普通技术选择抛给用户。
