# Task Execution

## 目标

让日常研发从“AI 帮我做一步”变成：

```text
用户给目标
  → 必要时 task-design
  → 设计 Review PASS（优先独立）
  → 用户确认 design.md
  → 生成 tasks.md
  → Agent 连续实现并验证
  → 实现 Review（优先独立）
  → 发现问题则自动返工
  → 全部通过后交付用户验收
```

默认**只在设计阶段设置人工确认闸门**；设计确认后，不要求用户逐任务确认，除非出现新的高成本设计变更或真正阻塞。

## 启动前

先读取：

- 项目规则：`AGENTS.md`、`CLAUDE.md`、rules、README
- 与目标相关的现有实现
- 已有 `work/任务/<任务名>/design.md`、`tasks.md`
- 可用时读取 `work-convention`
- 如果任务符合 `task-design` 的触发条件，先建立或更新 `design.md`

如果任务触发了 `task-design`：

- `设计审查 != PASS` → **禁止进入执行**，返回 `task-design` 完成其内置的设计对抗审查；
- `阻塞确认项 != 0` → **禁止进入执行**，先由用户做必要决策并回到 `task-design` 更新、复审；
- `设计审查 = PASS` 且 `设计确认 = 待确认` → **停止执行并等待用户确认**；
- 只有同时满足 `设计审查 = PASS`、`阻塞确认项 = 0`、`设计确认 = 已确认`，才允许创建 `tasks.md` 和修改业务代码；
- 用户若在“确认”时附带会改变高成本契约的条件，不视为已确认：先更新设计并重新 Review。

如果用户只是要求设计，不进入本 Skill。

## tasks.md

需要持续状态时创建：

```text
work/任务/<任务名>/tasks.md
```

没有 `design.md` 也可以存在 `tasks.md`；但任务涉及高成本契约时不能用任务清单替代设计。

创建时读取 `templates/tasks-template.md`。

### 建立代码基线

在修改业务代码前，尽量记录：

- 当前 branch
- 当前 HEAD / start commit
- 任务开始前已经存在的工作区修改（至少记录文件范围；无法可靠识别时明确写“未知”）

Git 不可用时不因此阻塞普通开发，但要明确基线不可得。

**不得为了让 diff 干净而 reset / checkout / revert 用户在任务开始前已有的修改。**

`task-execution` 本身不隐含 `commit`、`push`、`deploy/release`、生产环境写入或不可逆外部操作权限。只有项目规则已经明确允许，或用户明确授权时，才执行这些动作。

### 拆分原则

按**可独立交付、可独立验证的能力单元**拆，不按代码层拆。

好：

- “完成退款申请入口并保证重复请求幂等”
- “接通支付回调并覆盖成功/失败状态流转”
- “迁移历史字段并验证新旧数据一致”

不好：

- “写 Controller”
- “写 Service”
- “写 Mapper”
- “补几个 DTO”

默认只规划足够支撑当前目标的一层任务，不提前把所有代码细节拆到几十项。

每个任务至少包含：

- 目标
- 依赖
- 对应验收（有 `design.md` 时引用 `ACxx`）
- 验收标准
- 验证方式
- 状态

### AC 覆盖检查

有 `design.md` 时，开始实现前必须检查：

- 每个 `ACxx` 至少被一个 Task 或“最终核验”覆盖；
- 任务中的验收不能与 design 的 AC 相冲突；
- 允许存在支撑性任务没有直接 AC，但必须服务于被覆盖的能力，不能借机扩 scope。

发现 AC 漏覆盖时直接补齐 `tasks.md`，不需要因此打断用户。

## 执行状态

只使用：

- `pending`
- `in_progress`
- `blocked`
- `done`

同一时刻默认只有一个 `in_progress` 任务；满足下述安全并行条件时才允许多个互不依赖的任务同时处于 `in_progress`。

状态只写在 `tasks.md`，不要同步复制到 `design.md`。

## 多 Agent 执行策略

- **默认单 Builder 串行执行**；只有任务依赖已满足、文件 / 模块或数据写入范围互不冲突、可以分别验证且并行收益大于协调成本时，才委派并行实施。
- 并行任务在 `tasks.md` 中记录执行者和读写范围；禁止多个 Agent 同时修改相同文件、共享状态或迁移目标。依赖存在、边界不清或合并风险高时仍串行。
- 主 Agent 负责状态协调、合并冲突处理、集成验证和最终交付；不能用子 Agent 的“已完成”代替真实验证。
- Implementation Reviewer 保持独立优先、只读审查，不与代码修改同时产生冲突。运行器不支持子 Agent 时直接单 Agent 执行，不额外引入编排工具。
- 用户提示词可以覆盖本次并行偏好，但不突破设计确认、权限和数据安全边界；不预设子 Agent 个数。

## 主循环

### 1. 选择任务

默认选择第一个依赖已满足的 `pending` 任务，标为 `in_progress`。只有符合“多 Agent 执行策略”的独立任务才可并行启动，并分别维护状态和验证证据。

### 2. 实现

先读相关代码，再修改。

实现过程允许调整低成本细节；不要因为最初计划写得不够细就停下来问用户。

### 3. 验证

执行该任务声明的确定性验证，例如：

- 编译 / typecheck
- 单元测试
- API / 场景测试
- 数据库约束 / 校验 SQL
- lint / 架构检查
- 现有项目已有的验收命令

不能只根据“代码看起来对”把任务标为完成。

### 4. 处理失败

验证失败时：

1. 保持 `in_progress`；
2. 根据实际错误诊断；
3. 修复；
4. 重新验证。

如果连续多次失败但没有获得新的证据，默认第三次后停止盲目重试，记录根因和已尝试方案并标为 `blocked`。

### 5. 处理设计偏差

如果实现发现：

- 核心流程
- DB Schema / 核心数据
- 公共 API
- 权限
- 消息契约
- 迁移 / 兼容
- 并发 / 幂等 / 事务

等高成本契约需要改变：

1. 更新 `design.md`；
2. 将 `设计审查` 重新标为 `待审查`，`设计确认` 重新标为 `待确认`；
3. 暂停受影响任务；
4. 回到 `task-design`，重新执行其内置的设计对抗审查；
5. Review PASS、阻塞确认项清零后等待用户重新确认；
6. 再调整受影响的 tasks 和 AC 覆盖关系并继续实现。

低成本实现细节变化不回填设计，也不触发人工确认。

### 6. 完成任务

只有验收条件满足且验证通过后才标记 `done`，并记录必要的验证证据摘要。

然后自动进入下一个可执行任务。

## 什么时候找用户

默认不因为以下事情中断：

- 类怎么拆
- 方法怎么命名
- SQL 怎么写
- DTO 怎么组织
- 选用项目中已有的哪种同类实现模式

只有以下情况才进入 `blocked` 并找用户：

- 缺失业务规则会改变核心行为；
- 两个不可兼容方案都合理，且项目现状无法判断；
- 需要账号、凭据、授权或用户侧操作；
- 涉及不可逆外部动作、生产数据或明显安全风险；
- 环境本身不可用，Agent 无法继续验证。

## 对抗式实现审查闸门

所有普通实现任务都 `done` 后，**不能直接宣布完成**。

本 Skill 自己负责启动 Reviewer；不依赖额外 Review Skill。

Reviewer 规则：

- 优先使用独立 subagent / 独立上下文；
- 当前环境不支持独立 Reviewer 时，允许降级为 same-context 对抗审查；
- 无论使用哪种模式，都必须在 `tasks.md` 记录 `实现审查模式：independent | same-context`，不能把 same-context 伪装成独立审查；
- 不信任 Builder 的自报结果；
- **只找问题，不直接修改业务代码**；
- 读取已确认的 `design.md`、`tasks.md`、代码基线、当前代码 / Git diff 和真实测试 / 构建结果，尽量区分本任务变化与任务前已有变化；
- 尝试推翻“实现已经满足设计和验收标准，可以交付”。

重点攻击：

- design 契约、AC 与真实实现是否一致
- 非法状态、空值、重复请求、失败路径
- 权限绕过、幂等、并发、事务与部分成功
- 旧数据 / 旧接口兼容
- 外部依赖异常、超时、重试
- 回归和范围污染
- 测试是否假阳性、只覆盖快乐路径、或结果不是基于当前代码

Finding 分级：

- `Critical / High`：阻塞交付
- `Medium / Low`：记录，但不默认阻塞

每条阻塞 finding 尽量包含证据位置、违反的 design / 验收标准和复现或验证方式。

如果审查 `FAIL`：

1. 把 Critical / High finding 转成新的返工任务（如 `R01`、`R02`）追加到 `tasks.md`；
2. Builder 按正常主循环修复并验证；
3. 再启动 Reviewer 复审，仍优先 independent；不可用时允许 same-context 并明确记录。

Review PASS 条件：

- Critical = 0
- High = 0
- design 的所有 AC 已有真实覆盖证据
- 关键确定性验证通过
- 没有证据表明实现违反 design 或明确验收标准

默认最多连续 3 轮审查返工；仍未通过时标记 `blocked`，保留 findings 和证据，避免无限循环。

## 完成条件

只有同时满足才完成：

- 所有非阻塞任务为 `done`
- 有 design 时所有 AC 已被 Task / 最终核验覆盖，并有通过证据
- design 中声明的关键确定性验证已通过
- 项目必要且可执行的构建 / 测试通过
- 对抗式实现审查最终 `PASS`，且已记录审查模式
- Critical / High findings 为 0
- `tasks.md` 已更新为最终状态

## 中断与恢复

新的 Agent / 新会话恢复任务时：

1. 读项目规则；
2. 读 `design.md`（若存在）；
3. 读 `tasks.md`；
4. 核对 tasks.md 记录的 branch / start commit / 既有工作区修改；
5. 核对当前代码和 Git diff，区分本任务修改与任务前已有修改；
6. 不信任旧的 `in_progress` 自报状态，先验证真实代码；
7. 从第一个真实未完成且可执行的任务继续。

文件用于**恢复状态**，不代表 Claude Code / Codex 进程退出后会自己重新启动。

需要“进程挂了自动拉起、跨机器无人值守、定时继续、多个执行器并行”时，再由 Hermes / 外部 orchestrator 调度；它仍然可以复用同一套 `design.md + tasks.md` 协议。

## 回复约定

全部完成后再向用户做一次交付汇报：

```text
已完成：<目标>
设计：<design.md 或无>
执行：<tasks.md 或直接完成>
验证：<关键检查>
实现审查：PASS（independent | same-context）
AC 覆盖：<已覆盖 / 无 design>
遗留：<Medium/Low 或无>
```

存在 blocked 时只汇报真正阻塞继续执行的信息，不把普通技术选择抛给用户。
