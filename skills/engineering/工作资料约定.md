# 工作资料约定

> 普通仓库文档，**不是第三个 Skill**。这是辅助索引；设计和执行的实际规则以 `task-design`、`task-execution` 为准。

## 总体原则

- **优先项目现有约定**：已有 `dev/`、`docs/` 或其他工作目录时沿用，不批量迁移，也不建立第二套体系。
- 小 Bug、单字段、简单配置、短小可逆任务：直接在当前会话和代码中完成，不默认创建过程文档。
- 需要稳定设计与确认 → `task-design` 的 `design.md`；需要跨步骤/会话追踪 → `task-execution` 的 `tasks.md`。两者并非每个任务的必备文件。
- 设计和执行资料各有唯一权威来源；不持久化 Agent 思考过程、长日志或无复用价值的临时文件。

## 无项目现成约定时的可选目录

```text
work/
├── 任务/<任务名>/
│   ├── design.md      # 按需：稳定设计基线、AC、人工确认
│   └── tasks.md       # 按需：实施队列、验证、阻塞、恢复
├── 决策/              # 长期有效、跨任务或难以逆转的决策
├── 场景测试/          # 可复用的长期回归脚本和公共测试资料
├── 上线/              # 按需的上线专项资料
└── 归档/              # 不再活跃且有明确要求时归档
```

- `work/决策/<四位序号>-<中文决策名>.md` 记录背景、备选、最终取舍、代价与调整条件；可参考 [决策模板](task-design/templates/决策模板.md)。普通实现细节不另建决策文件。
- 一次性验证资料放任务目录，长期共用回归资料放 `work/场景测试/`；上线资料遵循项目惯例。
- `docs/` 保存长期稳定的产品或技术知识，`skills/` 保存可复用 Agent 工作规程，不用 `work/` 替代它们。
- 默认只需要 `design.md`、`tasks.md`，确需补充文档时必须从主文档链接，不为分类而分类。
- 不主动归档，除非用户要求或项目规则明确；归档不得破坏历史引用。

## 安全与维护

不覆盖已有资料，不保存未脱敏的敏感信息，不借整理文档改动业务数据或重置用户工作区。代码和文档冲突时先核实真实行为。提交、推送、部署及生产修改仍需单独授权。

> 旧 `work-convention` 已并入两个 Skill。安装器不会自动清理已安装副本，确认新版本可用后应手动移除，避免旧版本触发。
