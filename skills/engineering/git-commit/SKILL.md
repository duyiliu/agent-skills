# Git Commit

## 概述

将当前工作区转化为一个清晰的、原子的 Git 提交，默认使用中文 Conventional Commits 格式。默认最小化 Git 读取；非必要不查询提交历史，只在用户明确要求匹配仓库风格、提交消息风格确实不确定，或需要拆分多组提交时才读取近期 commit。始终生成标题和正文。展示提交消息后，提供给用户两个选项：**提交**（仅 commit）或 **提交并推送**（commit + push）。`git commit` 之前的所有输出均为提交前预览，非最终结果。

## 工作流程

1. 检查工作区：

   - 运行 `git status --short`。
   - 当变更规模或范围需要上下文时，运行 `git diff --stat`。
   - 在需要理解意图时，读取目标文件的 diff。
   - 默认不运行 `git log` 或读取提交历史。只有在用户明确要求匹配仓库风格、没有明确提交消息且风格无法判断，或需要按历史粒度拆分多组提交时，才读取近期提交。
   - **识别变更分组**：分析所有变更文件，按语义/功能域分组。例如 `feat`、`fix`、`docs`、`refactor` 分属不同提交的变更，归为不同组。同组内文件应属于同一个逻辑变更。
2. 总结提交前预览：

   - 明确标注为 "## 提交前预览"。
   - 列出将要提交的精确文件范围（如果可以确定）。
   - 给出核心变更的简洁总结。
   - 说明是否运行过验证。除非用户明确要求，否则不运行构建、测试、发布或其他耗时命令。
   - 在暂存前提示明显的可疑文件，如日志、临时文件、生成的 AI 产物、本地环境文件、构建输出或不相关的修改。
   - 在排除看起来像生成产物的文件前，通过 `.gitignore` 和 `git ls-files <目录>` 检查仓库约定；某些仓库有意跟踪生成的报告/数据快照。如果该目录下的历史文件被跟踪，则应暂存同类的新产物，除非它们被明确忽略或仅为运行时产物。
3. 生成提交消息：

   - **如果只有一组变更**：直接生成一条提交消息。
   - **如果有多组变更**：为每组分别生成提交消息。在上一条的展示基础上，按序号列出：
     ```text
     ## 提交计划（共 N 个原子提交）

     1. [组 A 的文件列表] -> type(scope): 摘要

        - 为了降低提交信息生成的随机性，固定正文的信息顺序
        - 将变更动机、核心调整、影响范围和验证状态收敛为自然语言要点
        - 影响 git 提交流程中的消息预览、确认和实际提交正文
        - 未运行验证：用户未要求执行测试或构建

     2. [组 B 的文件列表] -> type(scope): 摘要

        - 为了避免不同提交组之间的职责混杂，按语义边界拆分变更
        - 将同一功能域内的文件归入同一个原子提交
        - 影响多组变更场景下的提交计划和暂存范围
        - 未运行验证：用户未要求执行测试或构建
     ```
   - 消息模板使用“真实提交正文样例”，不要输出占位说明；示例只用于展示结构，不得复用示例中的具体业务内容：
     ```text
     type(scope): 摘要

     - 为了降低提交信息生成的随机性，固定正文的信息顺序
     - 将变更动机、核心调整、影响范围和验证状态收敛为四条自然语言要点
     - 影响 git 提交流程中的消息预览、确认和实际提交正文
     - 未运行验证：用户未要求执行测试或构建
     ```
   - 标题规则：
     - 默认使用中文，除非用户要求其他语言。
     - 如果用户已经提供明确提交消息，优先使用用户消息；不要为了重写风格而额外读取提交历史。
     - 使用 Conventional Commits 类型：
       - `feat`：新功能
       - `fix`：缺陷修复
       - `refactor`：保持行为不变的重构
       - `docs`：文档
       - `test`：测试
       - `chore`：维护
     - 当范围明确时优先使用 `type(scope): summary`，否则使用 `type: summary`。
     - `scope` 使用稳定模块名、目录名或能力名，例如 `git-commit`、`skills`、`docs`；不要使用过细的临时文件名。
     - 摘要只描述“完成后的状态变化”，不要写执行动作清单。
   - 正文规则：
     - **始终包含正文**，默认按“动机 / 变化 / 影响 / 验证”的语义顺序组织，但不要输出这些分类标签。
     - 每个要点只写一行，避免把 diff 逐项翻译成流水账。
     - 第一条解释决策依据，避免只写“优化”“调整”“完善”。
     - 第二条只保留 1-2 个核心变化，次要细节不进入提交消息。
     - 第三条明确边界，帮助 reviewer 判断影响面。
     - 第四条必须真实说明验证状态；除非用户明确要求，否则不要为了填充该字段而运行测试或构建。
   - 禁止项：
     - 避免模糊摘要，如 `update`、`fix bug`、`修改代码`、`更新一下` 或 `AI changes`。
     - 不要生成“本次提交”“此次变更”等低信息密度表述。
     - 不要在正文中复述文件名列表；文件范围已在提交前预览中展示。
     - 不要编造验证结果、issue 编号、性能收益或用户影响。
   - 只提供**一条**推荐方案，不提供备选。
4. 询问用户操作：

   - **优先使用问答工具**收集用户选择，而不是纯文本追问。
   - **单组变更**：通过问答工具提供两个选项：`提交` / `提交并推送`。
   - **多组变更**：通过问答工具提供三个选项：`全部提交并推送` / `全部提交` / `选择其中某组单独提交`。
     - 如果用户选择单组提交，再通过问答工具列出各变更组，让用户选择目标组，然后循环回到步骤 3-4-5 处理该组。
   - 等待用户确认后再执行。
   - 如果没有实质内容变更（例如只有 CRLF 行尾噪音），发出警告，并通过问答工具询问是否继续。
5. 执行：

   - **单组变更**：
     - 仅暂存选中的文件（优先使用显式路径而非 `git add .`）。
     - 对于多行消息，使用多个 `-m` 参数构建 commit 命令，并保持正文结构与预览消息一致：
       ```bash
       git commit -m "docs(git-commit): 优化提交消息生成模板" -m "- 为了减少提交正文中的模板化标签，改用自然语言要点组织信息" -m "- 将消息预览、正文结构和命令示例统一为四条提交说明" -m "- 影响 git-commit skill 的提交计划、消息生成和执行示例" -m "- 未运行验证：仅调整文档规则"
       ```
     - 如果用户选择了"提交并推送"，在 commit 成功后运行 `git push`。
   - **多组变更（原子化提交）**：
     - 按提交计划的顺序逐组处理。
     - 每组：暂存该组文件 -> git commit（用对应的消息）-> 继续下一组。
     - 全部提交完成后，如果用户要求推送，运行 `git push`。
     - 如果某组提交失败，停下来报告错误，询问是否继续下一组。
   - **推送被拒绝或远端领先**：
     - 不自动执行 `pull`、`merge` 或 `rebase`。
     - 先报告当前状态，并默认推荐 `git pull --no-rebase`，因为 merge 不改写本地提交历史。
     - 通过问答工具让用户选择：`merge 同步后继续推送` / `取消并手动处理` / `改用 rebase`。
     - 只有用户明确选择后，才执行对应同步操作。
   - **冲突处理**：
     - 如果 merge 或 rebase 产生文件冲突，立即停止。
     - 列出冲突文件，等待用户人工确认最终语义。
     - 不自动选择 `ours` / `theirs`，不自动删除冲突标记。
     - 内容冲突解决后，根据当前流程继续：merge 使用 `git commit`，rebase 使用 `git rebase --continue`。
   - 对于非 TTY agent 终端中的交互式 git 命令，设置 `GIT_EDITOR=true`（或 `GIT_EDITOR=:`）以避免编辑器提示超时。
   - 如果 commit 失败，检查错误并进行有针对性的修正，而不是盲目重复相同的命令。
6. 报告结果：

   - **单组变更**：包含最终提交消息和提交哈希，以及类似 `git show --stat --oneline -1` 的紧凑摘要。
   - **多组变更**：列出所有已成功提交的哈希和消息（逐条展示）。
   - 如果执行了推送，包含 `git push` 的结果。

## 可选提交正文元数据

默认不要追加 AI 辅助、审阅状态或类似元数据。只有用户明确要求记录 AI 辅助信息，或仓库规范要求此类元数据时，才在正文末尾追加，并保持中文、简洁、可验证：

```text
AI 辅助：是
审阅状态：已人工确认
验证状态：未运行验证，用户未要求执行测试或构建
```
