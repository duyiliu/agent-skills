# Work Convention

## 目标

本 Skill 只负责研发过程资料的**放置、分层和生命周期**，不重复定义设计方法或执行算法。

核心原则：

```text
短小、一次性、可逆       → 当前 chat
需要稳定设计基线         → design.md
需要持续执行状态         → tasks.md
既要设计又要持续推进     → design.md + tasks.md
长期稳定知识             → docs/
可复用 Agent 执行规程    → skills/
```

最重要的边界：

- `design.md` 回答：**要做成什么，哪些高成本契约已经确定。**
- `tasks.md` 回答：**现在要做什么、做到哪、如何验证、哪里被阻塞。**

不要把两种职责混在同一个文件里。

## 何时创建 work/ 资料

### 不创建

以下情况默认只在当前 chat 中完成：

- 小 Bug、局部排错
- 单文件或小范围修改
- 单条 SQL、简单配置、单字段改动
- 可在一个会话内直接完成且没有持续状态价值的任务

### 创建 design.md

由 `task-design` 判断需要稳定设计基线时创建：

```text
work/任务/<任务名>/design.md
```

典型原因：业务流程、状态、DB、公共 API、权限、消息、迁移、并发、兼容等高成本契约需要前置明确。

### 创建 tasks.md

满足任一条件时创建：

- 用户要求 AI 持续把一项研发任务做完；
- 一个目标需要拆成多个可独立验证的执行任务；
- 预计会跨会话继续；
- 需要在 Agent 中断后恢复“下一步做什么”；
- 需要记录验证结果、阻塞项或审查返工项。

默认路径：

```text
work/任务/<任务名>/tasks.md
```

### 同时存在

大多数“完整业务功能 + AI 自主实现”最终会形成：

```text
work/任务/<任务名>/
├── design.md
└── tasks.md
```

不要因为任务复杂就默认继续拆更多文件。

## 目录模型

```text
work/
  任务/
  决策/
  场景测试/
  归档/
  上线/
  README.md
```

项目已有自己的约定时优先沿用。已经使用历史 `dev/` 的项目继续使用原目录，不批量迁移、不创建第二套体系。

## design.md 职责

`design.md` 是稳定设计基线，由 `task-design` 负责内容。

应保存：

- 背景、目标、范围、非目标
- 关键业务流程和状态
- Data / DB
- API / 外部交互契约
- 权限、幂等、事务、兼容等高成本边界
- 风险
- AC 验收项与关键验证方式
- 阻塞确认项 / 非阻塞待确认项
- 设计审查状态（待审查 / PASS）
- 审查模式（independent / same-context）
- 设计确认状态（待确认 / 已确认）

**不要保存：**

- 当前阶段
- 最近进展
- 下一步
- 完成百分比
- 动态实施清单
- Review 返工队列
- Agent 流水账

当实现发现高成本契约变化时更新 `design.md`，并将“设计审查”重新置为“待审查”、“设计确认”重新置为“待确认”；普通代码进度变化不更新它。

对触发了 `task-design` 的任务，必须按以下顺序通过：

```text
task-design 内置 Design Review PASS
→ 阻塞确认项 = 0
→ 用户明确确认 design
→ 才能生成 tasks.md 并开始实施
```

设计审查是 AI 质量闸门，设计确认是人工决策闸门；两者都不属于 `tasks.md` 的动态执行状态。

设计内容和模板统一以 `task-design` 为准，`work-convention` 不再维护第二套设计模板。

## tasks.md 职责

`tasks.md` 是当前任务唯一的**动态执行状态源**，由 `task-execution` 维护。

应保存：

- 当前总体状态
- 可执行任务队列
- 代码基线（branch / start commit / 任务前既有工作区修改）
- AC → Task / 最终核验的覆盖关系
- 每个任务的目标、依赖、对应 AC、验收标准和验证方式
- pending / in_progress / blocked / done 状态
- 必要的验证证据摘要
- 对抗式实现审查状态与审查模式
- Review 产生的返工任务
- 当前阻塞及恢复所需信息

不要复制完整设计。只链接 `design.md` 并引用对应契约。

同一时刻只允许一个编排者负责写 `tasks.md`。如果未来使用并行 Agent，由上层编排者聚合状态，避免多个 Agent 同时改同一份任务队列。

## 补充文档

默认只保留 `design.md` 和 `tasks.md`。

只有内容确实膨胀、且存在独立长期价值时才增加补充文档，例如：

- 大型数据迁移方案
- 外部协议说明
- 大量验收证据
- 上线专项资料

规则：

1. 补充文档必须从 `design.md` 或 `tasks.md` 链接。
2. 一个主题只保留一个权威来源。
3. 不建立“为了分类而分类”的文档树。
4. Agent 的思考过程、长日志和临时输出不纳入长期文档。

## 决策资料

跨任务、难逆转或长期有效的决策放：

```text
work/决策/<四位序号>-<中文决策名>.md
```

每条决策至少记录：

- 背景和问题
- 备选方案
- 最终决策
- 关键权衡和后果
- 当前结论和关联任务

任务专属、低成本、可逆的取舍不要单独建决策文档。

## 场景测试与上线资料

- 长期回归脚本、公共 Mock 数据、统一执行入口：`work/场景测试/`
- 一次性任务验证资料：对应 `work/任务/<任务名>/`
- 上线专项资料：`work/上线/<日期>/`
- 本地临时输出默认不纳入 Git
- 生产配置不得依赖 `work/` 中的测试资料

## 归档

- 不主动归档，除非用户明确要求或项目已有规则。
- 归档前确认任务已完成且不再活跃。
- 归档时保留任务名和关键关联，避免历史引用断裂。

## 安全规则

- 不在目录名或正文记录未脱敏的真实个人敏感信息。
- 不覆盖用户已有资料。
- 不用 `work/` 替代项目已有的 `skills/`、`docs/`、`mcp/`、`config/` 分层。
- 不默认创建 `openspec/`，除非项目已有约定。
- 如果当前代码、运行结果与过程文档冲突：先核实真实状态，再修正文档；不要为了“保持文档一致”反向修改正确代码。
- 不为了制造干净 diff 而覆盖、reset、checkout 或 revert 用户已有修改。
- `task-execution` 不自动授权 commit / push / deploy / release / 生产写入 / 不可逆外部操作；权限来自项目规则或用户明确指令。

## 与其他 Skill 的关系

```text
task-design
  └─ 维护 design.md
      └─ 内置 Design Review（优先 independent）
          └─ 阻塞确认项清零
              └─ 用户确认设计（人工闸门）

task-execution
  └─ 设计已确认后维护 tasks.md
      └─ AC 覆盖 + 实现 + 确定性验证
          └─ 内置 Implementation Review（优先 independent）
              └─ 未通过 → 返工项回到 tasks.md
```

`work-convention` 只定义这些文件应该放在哪里以及各自的职责边界。

## 回复约定

创建或更新过程资料后只汇报必要信息：

```text
已创建/更新：<路径>
用途：<design 基线 / tasks 执行状态 / 决策 / 测试 / 上线>
后续：<继续执行或需要用户确认的阻塞项>
```
